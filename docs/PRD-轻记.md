## 二、产品定义

### 2.1 产品目标

> 以下 5 条直接承袭原型「关于轻记」弹窗中明示的产品价值观，是产品的灵魂，实现时不得丢失。

| # | 目标 | 说明 | 可度量标准 |
|---|---|---|---|
| G1 | **把「记一笔」压缩到 3 秒以内** | 打开即可输入：进入记账页默认停在支出态 + 默认分类已选中，只用敲数字 → 完成 | 从点击 FAB 到交易落库并可回首页看到，路径 ≤ 3 次点击；P0 阶段实测冷启动后完成一次记账 ≤ 8 秒 |
| G2 | **多账本分离，首页标题实时联动** | 日常 / 旅行 / 装修等场景分开记；切换账本后今日页标题、所有统计口径立即跟随 | 切换账本后，今日页标题与全部金额指标 100% 取自新账本，无需刷新 |
| G3 | **日历回溯：点哪天看哪天** | 月历每格显示当日总额，带记账热度底色，点击即看当天收支汇总与明细 | 月历渲染 ≤ 1 帧无卡顿；单日详情 0 延迟展示 |
| G4 | **结余视角替代传统预算压力** | 首页与统计页以「收入 − 支出 = 结余 / 结余率」作为主指标，而非"预算剩余" | 结余与结余率在所有周期（周/月/年）口径一致且可复算 |
| G5 | **预算默认关闭、按需启用** | 预算是可选能力而非常驻压力源；关闭时首页预算卡整卡隐藏 | 默认安装后首页不可见任何预算元素；仅在「我的 → 预算管理」开启后展示 |

## 三、需求池

**优先级定义**
- **P0（Must have）**：MVP 最小闭环 —— 能记账、能存、能看、能切账本。P0 未完成则产品不可用。
- **P1（Should have）**：完整还原原型体验所需的主体功能。
- **P2（Nice to have）**：增强项，可后置。

### 3.1 P0 —— MVP 最小闭环

|---|---|---|---|---|
| R01 | 工程骨架与底部导航 | Flutter 工程初始化；底部 5 Tab（今日/图表/日历/账本/我的）胶囊式导航；Tab 选中填充主色、文字 10px；滑入页（记一笔/预算/主题）以路由栈呈现 | P0 | 5 个 Tab 可切换且状态保持；切 Tab 不重建数据；滑入页可从任意 Tab 打开并可返回 |
| R02 | 本地数据层（SQLite） | 建库 + 账本/分类/交易/偏好 4 类表；首次启动写入默认账本与系统分类；提供 Repository 层（详见 §5） | P0 | 首次启动自动建库并播种；杀进程重启后数据完整保留；金额以「分」为 INTEGER 存储无精度损失 |

### 3.4 原型「假数据 / 原型演示」项的取舍汇总

原型中有 8 处 `toast('…（原型演示）')`，真机必须变为真功能或明确降级：

| 原型位置 | 原型行为 | 落地取舍 | 优先级 |

热度规则（务必精确还原）：
```

```

## 五、数据需求

> 供架构师设计 Schema。以下为**实体与关键字段**，不写建表 SQL。
> ⚠️ **全局约定：金额一律以「分」为 INTEGER 存储**（`amount_minor`），仅在展示层除以 100，避免浮点误差。

### 5.1 需持久化的实体

| 实体 | 说明 | 关键字段 |
|---|---|---|
| **book 账本** | 多账本容器 | `id`、`name`、`icon_key`、`icon_color`、`sort_order`、`is_default`、`created_at`、`updated_at`、`archived` |
| **category 分类** | 系统预置 + 用户自定义 | `id`、`name`、`type`（1=支出 / 2=收入 / 3=转账）、`icon_key`、`color_bg`、`color_stroke`、`sort_order`、`is_system`、`enabled`、`book_id`（NULL=全局通用） |
| **transaction 交易** | 核心事实表 | `id`、`book_id`、`category_id`、`type`、`amount_minor`（分）、`note`、`tx_date`（`YYYY-MM-DD`，本地日期）、`tx_time`（`HH:mm`）、`created_at`、`updated_at` |
| **budget 预算** | 每月预算开关与金额 | `id`、`book_id`（NULL=全局，见 Q4）、`monthly_amount_minor`、`enabled`、`updated_at` |
| **preference 偏好** | KV 形式的应用设置 | `theme_id`、`current_book_id`、`reminder_enabled`、`reminder_time`、`last_backup_at`、… |

> 说明：原型中 `books`、`cats` 是内存常量；真机需落库且允许用户扩展。

### 5.2 索引与聚合需求（供建索引参考）

高频查询模式决定索引：
- `transaction (book_id, tx_date)` —— 今日页/日历页/账本统计均按「账本 + 日期区间」扫描
- `transaction (book_id, tx_date, type)` —— 收支分开聚合
- `transaction (category_id)` —— 图表页分类构成
- `transaction (tx_date)` —— 连续打卡计算（跨账本，见 Q2）

### 5.3 派生指标口径（**必须严格定义，否则各页数字会打架**）

| 指标 | 口径 | 备注 |
|---|---|---|
| 本月支出 / 本月收入 | `SUM(amount_minor) WHERE book_id=当前 AND tx_date ∈ 本月 AND type=支出/收入` | 转账不计入（P2 后） |
| 本月结余 | 本月收入 − 本月支出 | 可为负 |
| 结余率 | 结余 / 收入 × 100；**收入 = 0 时显示「—」**（禁止除零） | 原型 8713.5/12000 = 73% |
| 日均支出 | 本月支出 / **本月已过天数**（含今天）；查看历史月份时为 / 当月总天数 | 原型 3286.50/14 = 234.75 ✓ |
| 较上月 | ⚠️ **存在歧义，见 Q5**。原型是「本月至今 vs 上月整月」，会误导；建议改为「本月至今 vs 上月同期（1 号~同一天）」 | 必须在实现前定案 |
| 今日支出 / 今日笔数 | `SUM / COUNT WHERE tx_date = 今天 AND type=支出` | |
| 日历当日金额 | 当日支出（有支出时显示支出，纯收入日显示 `+收入`） | |
| 日历热度基准 | 当月**最大单日支出** | |
| 账本总笔数 | `COUNT(transaction) WHERE book_id=X` | |
| 账本累计支出 | `SUM(amount_minor) WHERE book_id=X AND type=支出` | |
| 账本更新时间 | `MAX(created_at)` → 展示「更新于今天 / X月X日 / XXXX年X月X日」 | |
| **连续打卡天数** | 从**今天**（若今天无记录则从昨天）向前回溯，连续「有交易的自然日」天数；今天和昨天都无记录则为 0 | 原型 21 天 |
| **已坚持记账天数** | ⚠️ **口径待定，见 Q1**。候选：① 首次记账日 → 今天的自然日跨度；② 有记账的不同日期数。原型「128 天 + 326 笔」与「374 笔 + 21 天打卡」自相矛盾，无法反推 | 必须定案 |
| 同比 | 本期 vs **去年同周期**（年维度：今年 vs 去年） | 无基期数据显示「暂无对比数据」 |
| 环比 | 周维度：本周 vs 上周；月维度：本月 vs 上月；**年维度：今年 vs 上半年**（原型标签为「半年环比」） | 同上 |

### 5.4 技术约束与选型建议

| 项 | 约束 / 建议 |
|---|---|
| 存储 | SQLite（Android 原生）。建议 `sqflite`；若 pub 不可达，退路为 `sqflite_common_ffi` 或直接手写平台通道 |
| 图表 | **强烈建议用 `CustomPainter` 自绘**（环形/仪表 = `drawArc`，柱状 = `RoundedRect`），避免引入 `fl_chart` / `syncfusion` 等重量级图表库 —— GitHub 不可达下包获取有风险，且原型图表形态简单，自绘可控性更高 |
| 图标 | **建议不用 SVG 依赖**（原型分类图标是 SVG path）。方案：以 Material Icons / Cupertino Icons 的 `IconData`（codePoint + fontFamily）存入 `icon_key`，配合固定色板渲染。若必须像素级还原原型线条图标，再评估 `flutter_svg` 可用性 |
| 主题 | 用 `ThemeExtension` 定义 18 个 Token（对照原型 CSS 变量），全局注入；禁止组件内硬编码色值 |
| 状态管理 | 由架构师定；建议轻量方案（ChangeNotifier / Riverpod），数据量小（单用户本地） |
| 金额 | 全程 `int`（分），展示层统一 `NumberFormat` 千分位 + 2 位小数；日历紧凑格式单独一套（≥1000 取整千分位，否则去尾部 `.0`） |
| 平台 | `minSdk` / `targetSdk` 由架构师定（若做 R23 通知提醒，Android 13+ 需 `POST_NOTIFICATIONS`） |

## 六、待确认问题

> 以下均为实现前必须定案的问题，按影响面排序。Q1–Q5 建议在架构设计启动前由用户拍板。

| # | 问题 | 背景 / 冲突点 | 建议方案 |
|---|---|---|---|
| **Q1** | 「已坚持记账 N 天」的口径是什么？ | 原型出现「我的页：326 笔 / 128 天」与「账本页统计：374 笔 / 21 天打卡」，**两处笔数与天数互相矛盾**，且均未说明计算方式 | 建议：①「坚持天数」= 首次记账日至今的自然日跨度；②「连续打卡」= 连续有记账的自然日数（见 §5.3）。并**统一全 App 笔数口径**（当前账本 vs 全部账本需明确） |
| **Q2** | 连续打卡与坚持天数，是**按单个账本**还是**跨全部账本**统计？ | 原型「我的页」显示的是全局指标，但「账本页」也显示「连续打卡(天)」，二者并列 | 建议：**连续打卡/坚持天数均按当前账本**（与账本切换联动，符合 G2）；若产品希望全局，则需两处区分为「本账本打卡」与「全局坚持」 |
| **Q3** | GitHub 不可达下，第三方包如何选型？ | 若 pub 镜像也不通，则只能用 Flutter SDK 内置能力 + 手写平台通道 | 请架构师**先验证 pub 可达性再定依赖清单**；本 PRD 已按「低依赖」设计（图表自绘、图标用内置 IconData）。若 `sqflite` 都装不上，需立即上报 |
| **Q4** | 预算是**全局**还是**按账本**？ | 原型预算管理页无任何账本选择入口，但产品又是多账本架构 | 建议 **P1 先做全局**（与原型一致，实现简单）；若按账本更符合直觉，则预算表加 `book_id` 并在预算页加账本选择器。请用户定 |
| **Q5** | 「较上月 ±N%」的对比基期？ | 原型：本月至今(¥3286.50) vs 上月整月(¥3735.00) = −12%。但本月只过了 14 天，与整月比必然"下降"，**会误导用户** | 建议改为**同期对比**：本月 1 号~今天 vs 上月 1 号~同一天。或保留整月对比但在 UI 上标注「vs 上月全月」。请用户定 |
| **Q6** | 首次启动是否内置示例数据？ | 原型把"今天"硬编码为 2026-10-14 并预置 10 天交易，掩盖了空态 | 建议：**首次启动为空**（提供「记第一笔」引导），另在设置里提供可选的「载入示例数据」开关，方便演示与截图 |
| **Q7** | 交易编辑/删除（R17）是否要提到 P0？ | 原型无此设计，但记账 App 记错无法改会显著影响体验 | 建议 P1。若用户认为属刚需，可上提 P0（会增加约 1 个页面 + 1 个确认弹窗的工作量） |
| **Q8** | 转账（R24）在 P0/P1 如何呈现？ | 原型三态含「转账」，但真实实现需新增**账户**实体（原型完全没有账户概念） | 建议：P0/P1 保留「转账」按钮但点击后明确提示「转账功能暂未开放」，**不要假保存**；P2 引入账户表后完整实现 |
| **Q9** | 用户昵称「清风」从哪来？ | 原型硬编码，无账号体系 | 建议：本地偏好中存 `nickname`，默认「轻记用户」，可在「我的 → 用户卡」点击后编辑（原型用户卡带右箭头，暗示可点） |
| **Q10** | 分类图标是否必须像素级还原原型 SVG？ | 原型 8 个支出分类均为手绘线条 SVG path，无现成图标库对应 | 建议：优先用内置图标近似（成本 0、无依赖风险）；若用户要求像素级还原，再引入 SVG 方案（受 Q3 影响）。请用户定优先级 |
| **Q11** | 是否需要多币种 / 是否需要统计期自定义（如自定义起止日期）？ | 原型无 | 建议：P0-P1 单币种（CNY）、固定周/月/年三档；自定义区间放 P2 |
| **Q12** | Android 打包与分发方式？ | PRD 未涉及 | 需确认：仅本地 debug/自签 release APK，还是需要签名配置 + 应用商店上架（影响 keystore 与 targetSdk 要求） |
